# ドキュメント体制の見直し (specs 運用 / design 整理 / DesignDoc 記述方針) 要求定義

## チケット情報

- 起点: 自由文 (ユーザーヒアリング 2026-07-25)
- チケットID: #31
- トラッカー: GitHub (Fukuemon/kufu-apps)
- URL: https://github.com/Fukuemon/kufu-apps/issues/31

## 背景・目的

設計文書群の運用に次の課題感がある:

1. **specs の存在意義**: SDD 運用上 spec は issue 単位の作業文書で close 時に削除する契約だが、実際には close 済み issue 分の 9 ディレクトリが `specs/` に残存している。当初は spec という中間文書の廃止 (design / ADR への集約) も検討したが、2026-07-25 の再確認で **spec 運用は現行契約のまま存続し、closeout (close 時削除) の徹底を是正する** 方針に確定した (決定事項 #1)。
2. **design 内の陳腐化**: `design/` 配下に不要なドキュメント・記述が疑われる。特に Pencil ファイル (`design/features/corporate-site/index.pen`) は実装の更新に追従できておらず実態と乖離している。実装を正として削除する選択肢も検討したい。
3. **DesignDoc の記述方針**: DesignDoc.md に Phase 1/2/3 という時系列の phase 記述が多数あるが、設計文書は「今の事実」だけを記載すべきではないか。また C4 図 (System Context / Container) が読んでも要点が掴みにくい。

## 想定ユーザー/ステークホルダー

| 区分            | 対象                    | 関心事                                                          |
| --------------- | ----------------------- | --------------------------------------------------------------- |
| 開発者 (本人)   | リポジトリ管理者        | 文書のメンテナンスコストを下げ、実装と乖離しない状態を保ちたい  |
| AI エージェント | SDD workflow の実行主体 | 正本文書が少なく・新鮮で・矛盾がないほど設計/実装の精度が上がる |

## 提供価値(成功条件)

- 文書の種類と正本境界が削減・単純化され、「どこを読めば今の事実が分かるか」が一意になる
- 実装と乖離した文書 (Pencil / 古い spec / phase 記述) が残らない運用になる

## スコープ

### やること (決定済み方針の詳細化と正本反映まで)

- specs closeout 徹底の是正: 残存 9 ディレクトリの sync 状況確認 → 清算手順の文書化 → 全件削除の実施 (2026-07-25 clarify D3 でスコープ拡大)、close 時削除を担保する検査スクリプトの設計
- Pencil 削除の影響整理 (design-workflow / ADR-0004 の改訂方針)
- DesignDoc 書き換え方針の具体化 (現状事実のみ化の対象節の特定、将来計画の Future Work 節への一元化、C4 図 (L1/L2) の内容再設計)
- 決定の ADR / DesignDoc / context への反映

### やらないこと

- DesignDoc の大規模な書き直しや Pencil 等 specs 以外の文書削除の実施 (方針決定後に別 issue で実施。ただし決定に伴う軽微なメタ情報更新は可。specs の清算削除は上記のとおり本 issue で実施)
- sdd-template repo 側の skill / rule 本体の改修 (必要なら派生 issue)

| 1   | 決定は ADR に 1 判断 1 ファイルで記録する                               | 逆戻り防止                           | specs 存廃・Pencil 正本扱い・phase 記述方針は各々独立の判断 |

## 受け入れ基準 (EARS 風)

- WHEN 本 issue が完了したとき、システム (文書群) は specs 存続 + closeout 徹底 (廃止案の却下理由を含む) の判断と、残存 spec の清算手順・削除を担保する運用 / 検査の方針を ADR として保持している。
- WHEN 本 issue が完了したとき、システムは Pencil 削除 (実装を正とする) の判断を ADR として保持し、design-workflow (ADR-0004 / context/design-workflow.md) の改訂方針を示している。
- WHEN 本 issue が完了したとき、システムは DesignDoc を現状事実のみに書き換える方針 (将来計画の集約先を含む) と C4 図 (L1/L2) の内容再設計方針を保持している。
- WHEN 本 issue が完了したとき、`specs/` に close 済み issue の spec ディレクトリが残存していない (残存 9 ディレクトリの清算完了)。
- IF specs の清算手順 (残存 9 ディレクトリごとの sync 済み確認) が文書化されていない場合、THEN 実削除を行わない。
