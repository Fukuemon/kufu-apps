## 背景・目的

コーポレートサイトの文言・コンテンツについて、ステークホルダーから Excel 形式で FB を受領した。
サイトに表示されている文言の実体は `apps/corporate-site/src/content/` 配下のデータモジュールで、
その内容は `design/features/corporate-site/reference/` 配下の一次資料 (会社概要・取扱メーカー一覧) を出典としている。

FB は表示文言に対する指摘であるため、**表示側だけを直すと出典資料と実装が乖離する**。
出典資料と実装データの両方を同じ変更で更新し、`sourceReferences` による出典追跡の一貫性を保ったまま反映することが目的。

FB 原本は `.ai-out/FB/` にローカル共有され、全 63 件を抽出済み。個別項目は
[feedback-inventory.md](feedback-inventory.md) が正本 (A: ホームページ 8 件 / B: メーカー一覧 55 件)。

FB は文言差し替えにとどまらず、事業の説明構造を**「販売・加工の 2 本柱」から「販売・加工・小規模工事の 3 本柱」へ**
変更する内容を含む。これはユーザー確認のうえ本 issue のスコープに含める。

## 想定ユーザー/ステークホルダー

- **サイト来訪者 (製造現場の調達担当者)**: 正確で分かりやすい文言により、取扱範囲と相談可否を判断できる
- **FB 提供者 (事業側ステークホルダー)**: 自社の実態と一致した表現でサイトが公開されている状態を求める
- **開発者**: 出典資料と実装データの対応関係を壊さずに文言を更新できる状態を維持したい

## 提供価値(成功条件)

- FB 全 63 件が 1 件ずつ「反映済 / 対応不要 (理由付き)」に仕分けされ、取りこぼしがない
- 反映後も出典資料 (`reference/`) と実装データ (`src/content/`) の内容が一致している
- 既存の自動検査 (`pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm e2e`) が通る

## スコープ

### やること

- Google Drive の Excel から FB 項目を抽出し、対象箇所ごとに一覧化する
- `apps/corporate-site/src/content/` 配下のコンテンツデータの文言修正
  (`hero.ts` / `business.ts` / `company.ts` / `consultation.ts` / `contact.ts` / `services.ts` /
  `product-groups.ts` / `product-categories.json` / `category-makers.json`)
- 出典資料 (`design/features/corporate-site/reference/company-profile.md` / `manufacturers.md`) の同期更新
- 「小規模工事」を事業の第 3 の柱として追加する (サービス一覧 03 / 事業内容セクション見出し / 「小規模工事　事例」セクション新設)
- メーカー 4 件の削除に伴う件数更新 (`content-data.test.ts` の 323 → 319、各カテゴリの「取扱メーカー N社」表記)
- 文言に依存する Storybook story / E2E アサーションの追随

### やらないこと

- 既存セクションのレイアウト・デザイン変更 (配色やコンポーネント構造の作り替え)
- 新規ページの追加 (必要と判明した場合は別 issue に切る)
- CMS 化・コンテンツ入稿基盤の整備 (`apps/cms` は別スコープ)
- 画像・ロゴなどアセットの差し替え (FB に含まれる場合は別 issue に切る)

## 業務ルール

| #   | ルール                                                                                | 理由                                                        | 備考                                    |
| --- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------- |
| 1   | 表示文言の実体は `src/content/` 配下のデータモジュールに置き、`.astro` に直書きしない | コンテンツと表示の分離を保つ (既存構造の踏襲)               | `src/components/sections/` は参照のみ   |
| 2   | コンテンツ変更時は出典資料 (`reference/*.md`) を同じ変更で更新する                    | `sourceReferences` が指す出典と実装が乖離すると追跡が壊れる | `source-references.ts` が出典パスの正本 |
| 3   | 全コンテンツグループは `sourceReferences` を保持し続ける                              | `content-data.test.ts` が全件で検査している                 | 出典が増える場合は配列に追加する        |
| 4   | 製品カテゴリとメーカーは同一 ID 体系で対応づける                                      | 片側だけ増減すると整合検査が落ちる                          | `categoryId` で 1:1 対応                |
| 5   | FB 項目は「反映済 / 対応不要」のいずれかに必ず仕分けし、判断理由を残す                | 取りこぼしと「なぜ直さなかったか」の消失を防ぐ              | 仕分け表は本文書の該当節に追記する      |

## 権限要件

- 静的サイトのコンテンツ更新であり、アプリケーション内のロール制御は存在しないため**対象外**。
- ただし FB 原本の閲覧権限は作業者に必要 (`.ai-out/FB/` に共有済み)。

## 監査/非機能要件

### 監査・運用

- FB 項目と反映結果の対応が、本文書の仕分け表と PR 差分から追跡できること
- 出典資料の変更は commit 単位で追える形にする (実装データと同一 PR にまとめる)

### 非機能(性能/可用性/セキュリティ/保守)

- **性能**: 新設する「小規模工事　事例」セクションも静的に描画し、React island を増やさない
- **セキュリティ**: 公開サイトに載る情報のみを `src/content/` に置く。非公開の連絡先・個人情報を repo に持ち込まない
- **保守**: コンテンツと出典の 1:1 対応を維持し、次回 FB でも同じ手順で反映できる状態を保つ

## 受け入れ基準 (EARS 風)

1. WHEN FB Excel の各項目を確認したとき、システム (作業成果物) は当該項目を「反映済」または「対応不要 (理由付き)」のいずれかに仕分けした一覧を提示する。
2. WHEN 文言修正がコンテンツデータに反映されたとき、システムは該当ページを表示した際に修正後の文言を表示する。
3. WHILE 出典資料と実装データの両方が存在する間、システムは両者の内容が一致した状態を保つ。
4. IF コンテンツの件数 (製品カテゴリ / メーカー) が変わった場合、THEN システムは `content-data.test.ts` の期待値を同じ変更セット内で更新し、`pnpm test` を成功させる。
5. IF FB が新規ページ追加またはアセット差し替えを要求している場合、THEN システムは本スコープ外として別 issue に切り出し、本 issue には反映しない。
6. WHEN 反映後に `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm e2e` を実行したとき、システムはすべて成功する。
7. IF FB 内容が既存の出典資料と矛盾する場合、THEN システムは該当項目を保留とし、未決事項として FB 提供者への確認を残す。
