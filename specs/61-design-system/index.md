# DADS と buddy を参考に、Kufu の感じを残したデザインシステムで画面を作れる

## Requirements

要求は [issue 61](https://github.com/Fukuemon/kufu-apps/issues/61) にある。

## Non-Goals

次のものは、ほかの要求が決める。

- corporate-site の画面の構成と文言の変更
- ディレクトリ構成とツールチェーン（[issue 60](https://github.com/Fukuemon/kufu-apps/issues/60)）。この spec は、issue 60 の決定（`vp check`、`vp test`、文書は `docs/` の下、package はソースを export する）を前提にする。
- 配信の基盤とサブドメイン（[issue 47](https://github.com/Fukuemon/kufu-apps/issues/47)）。カタログの公開先のドメインは、基盤の決定に従う。
- E2E のテストの層と、section のアクセシビリティの確認（[issue 62](https://github.com/Fukuemon/kufu-apps/issues/62)）
- 問い合わせフォームの画面と送信（[issue 26](https://github.com/Fukuemon/kufu-apps/issues/26)）
- Kufu の色、書体、ロゴそのものの変更
- ダークモード

## Acceptance Criteria

issue 61 の受け入れ条件を使う。

### 論点 6: 14px より小さい文字と、文字の大きさの段

14px より小さい文字が約 70 か所ある。DADS は、本文と UI の文字を 16px 以上、補足を 14px とし、14px 未満を原則として認めない。

| 案        | 内容                                                                                                                            | 強み                                                     | 弱み                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------- |
| A（推奨） | 本文と操作の文字は 16px、補足は 14px に上げる。mono の eyebrow と番号のラベルだけ、12px の 1 つのスタイルとして残し、理由を書く | 読む文は DADS の基準を満たす。工業的なラベルの印象が残る | 約 70 か所の見た目が変わる。12px の例外が 1 つ残る |
| B         | 全ての文字を 14px 以上にする                                                                                                    | DADS の基準どおりで、例外がない                          | eyebrow が大きくなり、印象が最も変わる             |
| C         | 今の大きさを全て残し、理由を文書に書く                                                                                          | 見た目が変わらない                                       | 10px の文字と 13px の本文が残る                    |

- どの案でも、見出しの大きさは、DADS の文字の大きさの段から今の値に最も近い段を選ぶ。差は 3px 以内である（34px は 36px に、42px と 44px は 45px に、56px は 57px になる）。
- 色、書体、ロゴの変更ではないが、Kufu の感じに関わる。変えた後の画面は、運営者が VRT の baseline を見て決める。
- 決まらないと進めない作業: T5。
- 案は、ADR-0030 にある。

## Decisions

運営者が、2026-11-10 に決めたこと。

- shadcn（CLI と `shadcn/tailwind.css`）と Base UI を外し、ネイティブの要素で書く。
- `class-variance-authority` と `tailwind-merge` を外し、class の組み立ては `clsx` だけにする。見た目の変え方は `variant` のような props で決め、呼び出す側から class で上書きしない。
- shadcn の語彙のトークンを、DADS の考え方のセマンティックトークンに置き換える。ADR-0007 と ADR-0010 は、新しい ADR で置き換える。
- Kufu の色、書体、ロゴは変えない。
- ADR の番号は、0027 から使う。

### デザインシステムの文書の骨組みの案

骨組みは、導入のスキル setup-design-system のテンプレートをコピーし、スキル write-design-system で埋める。置き場は、論点 9 のとおり。

| ファイル                           | 書くこと                                                                                                                                                                    |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/ui/DESIGN.md`            | 話題ごとの文書、知りたいことごとの参照先、DADS との関係（任せる値と変えない要件）、原則、原則と確認の方法の対応、画面を作るときの手順、アクセシビリティ、決まっていない選択 |
| `packages/ui/design/tokens.md`     | 色（面、文字、枠、操作、フォーカス、状態）の名前と使う場面、暗い面、文字のスタイル、余白の段、ブレークポイント、角丸、影、動き。Kufu の色と書体の使う場所                   |
| `packages/ui/design/components.md` | コンポーネントごとの、使う場面、使わない場面、変種、状態、内容の制約、キーボードの操作                                                                                      |
| `packages/ui/design/catalog.md`    | カタログのページ、title の決め方、カタログに載せてよいもの                                                                                                                  |

- 原則の ID の案は、buddy と同じ 10 個にする。
  - 色と文字: `COLOR-TOKEN`、`STATE-NOT-COLOR-ONLY`、`TEXT-MIN-SIZE`
  - 操作: `PRIMARY-ACTION-ONE`、`FOCUS-ONE`、`TARGET-SIZE`
  - 並べ方と動き: `SPACING-SCALE`、`LAYOUT-OVERFLOW`、`MOTION-TOKEN`、`MOTION-REDUCE`
  - `LAYOUT-OVERFLOW` と `MOTION-REDUCE` を E2E で確認するかは、E2E のテストの設計で決める。それまでは、確認の方法をレビューにする。
- DADS から外れる 5 つの点（ADR-0030）は、理由と一緒に、その規則を持つ文書に書く。
- 「決まっていない選択」に、最初に書くもの
  - 本文の中のリンクの色と下線、訪問済みの色。今は、リンクが文字の色を引き継ぎ、下線を持たない。DADS は、色だけでリンクを示さないことを求める。
  - 成功と注意の状態の色。使うコンポーネントがまだ無い。
- corporate-site の Design Doc の「デザイントークン」と「トーンとマナー」は、デザインシステムの文書へ移し、Design Doc からリンクする。

### 実装のタスクの分け方

種別 design-system のプリセットに従い、子のタスクを、実装の 8 件と文書の 1 件にする。この pull request が、設計のタスクに当たる。
