## 背景・目的

デザイン制作を本格化するにあたり、「ワイヤー作成 → デザインシステム定義 → 実装」を **Claude Design → Pencil.dev → AI Agent (Claude Code / Codex)** で回す想定がある。現フロー（Astro 静的生成 + [packages/ui](../../packages/ui/) の shadcn/ui トークン正本 + [#11](https://github.com/Fukuemon/kufu-apps/issues/11) で確定済みの IA）に対し、この3ステップが最適か、代替（Figma + MCP）と比較して確定し、**プラットフォーム共通のデザイン制作ワークフローを正本化** することが目的。

デザインシステムの _中身_（トークン定義）は [#13](https://github.com/Fukuemon/kufu-apps/issues/13) が担う。本 issue はデザインを _どう作るか_ の **プロセス / ツール選定** を担う。

## 想定ユーザー/ステークホルダー

- プロダクトオーナー / 非デザイナー（founder・PM 視点での方向性決定）
- 実装担当（AI Agent と協働するエンジニア）
- デザインシステム保守者（`packages/ui` トークン正本のオーナー）

## 提供価値(成功条件)

- app / feature 横断で再利用できる Kufu 標準のデザイン制作ワークフローが正本化される。
- デザインシステム正本（`packages/ui`）をツールが消費し fork しない原則が明文化される。
- 方向性探索（発散）から実装（収束）までのツール境界が明確で、成果物の正本所在が一意。

## スコープ

### やること

- ツール比較（Claude Design / Pencil.dev / Figma+MCP）の結論を ADR 化する（`adr/0004-design-production-workflow.md`）。
- 確定ワークフロー（phase A 発散 / B 収束 / C 実装、ツール境界、`.pen` の Git commit 方針、feature doc への back-propagation 手順、Figma fallback 条件）を `context/design-workflow.md` に文書化する。
- ツール導入・環境設定（Claude Design アクセス枠 / Pencil + MCP セットアップ）。
- corporate-site の1ページでフローを実走するパイロット検証。

### やらないこと

- デザイントークンの中身定義（= #13）
- corporate-site 本体実装（= #10）
- Storybook 構築（= #6）

## 業務ルール（ワークフロー規約）

| #   | ルール                                                               | 理由                                        | 備考                       |
| --- | -------------------------------------------------------------------- | ------------------------------------------- | -------------------------- |
| 1   | デザインシステム正本は `packages/ui`（トークン+コンポ）に一元化      | Decision Priority「一貫性」/ drift 防止     | ツールは消費し fork しない |
| 2   | Claude Design 出力（HTML）は使い捨て、方向性決定のみ採用             | preview 段階で正本にしない                  | commit しない              |
| 3   | Pencil の `.pen`(JSON) は repo に commit し Git 管理                 | 「正本は repo 内」方針 / 外部 SaaS 依存回避 | バージョン管理対象         |
| 4   | 実装後、durable な設計判断は feature doc / トークンへ back-propagate | 正本境界の維持                              | design 側が正本            |

## 権限要件

- 該当なし（公開コーポレートサイトの制作プロセス。ロール別アクセス制御の対象外）。

## 監査/非機能要件

### 監査・運用

- ツール選定の根拠は ADR-0004 に記録し、変更時は ADR を更新する。

### 非機能(性能/可用性/セキュリティ/保守)

- 性能: 実装フェーズの成果は Astro 静的生成・最小 island（Decision Priority「パフォーマンス」）を維持する。
- 保守: ワークフローは特定 app に依存せずプラットフォーム共通で再利用可能であること。
