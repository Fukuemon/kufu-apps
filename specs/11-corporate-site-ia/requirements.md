## 背景・目的

- issue #3 で `apps/corporate-site` の Astro skeleton は成立済み。次の本命 #10 (本体実装) に入る前に、記載内容 (情報設計) の構成方針を先に固めたい。
- いきなり実装に入ると、ページ / section / コンテンツの粒度が場当たり的になり、`apps/corporate-site` の一貫性 (Decision Priority「一貫性」) を担保できない。
- 提供された企業情報 (有限会社フクウラ: 機械工具・省力化機器の見積/販売 + 各種加工) を素材に、**何のページを・どの優先順位で・どんな section で構成するか** を確定する。
- 関連: [Design Doc `## Why / What`](../../design/DesignDoc.md#why--what) 「コーポレートサイト要求」、[design/features/corporate-site/DesignDoc_corporate-site.md](../../design/features/corporate-site/DesignDoc_corporate-site.md) 「データ / コンテンツモデル」。

## 想定ユーザー/ステークホルダー

| 種別         | 説明                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| 主要訪問者   | フクウラへ機械工具/加工を発注検討する B2B の取引先・見込み顧客の担当者 |
| 副次訪問者   | 取引可否を判断する仕入/購買担当、既存取引先の窓口確認                  |
| サイト運用者 | コーポレートサイトのセクション/文言を更新する開発者・運用者            |
| 後続実装者   | #10 (本体実装) / #6 (Storybook) を担当する開発者・AI エージェント      |

## 提供価値(成功条件)

- 訪問者が「フクウラは何ができる会社か (販売×加工)」と「信頼できるか (沿革・理念・所在)」を、迷わず短時間で把握できる。
- ページ / section 構成が文書化され、#10 の実装が情報設計を再考せずに着手できる。
- 主目的は **事業内容の訴求** と **信頼性の確立**。問い合わせ導線は全ページから到達可能な副次目標として配置する。

## スコープ

### やること

- コーポレートサイトの **ページ一覧** と各ページの **section 構成 / コンテンツ粒度 / 優先順位** を定義する。
- グローバルナビゲーション / 主要導線 (問い合わせ CTA) の配置方針を定義する。
- 企業情報.md の各データ項目を、どのページ / section に割り当てるかのマッピングを示す。
- 追加予定コンテンツ (アクセス/地図、沿革、代表挨拶) の置き場所を IA に組み込む。
- 成果の feature doc (`design/features/corporate-site/DesignDoc_corporate-site.md`) への反映方針を示す。

### やらないこと

- デザイントークン (配色 / タイポ / spacing 等) の定義 — issue #11 の別側面として切り出し、別 requirements / spec で扱う。
- 実装手順 (Astro ページ配置 / client directive 判断 / `packages/ui` 昇格 / E2E の書き方) — spec / 実装フェーズへ委譲。
- 問い合わせフォームの機能仕様 (送信処理 / バリデーション / スパム対策) — IA 上は P6 に「設置する」(Q4)が、機能仕様は別 spec で扱う。
- 採用情報ページ (Q5 決定: 今回スコープ外。将来必要になれば IA を拡張)。
- 実コンテンツの本文ライティング (キャッチコピー等の最終文言)。
- CMS 化 (Phase 2 以降、[cms.md](../../design/features/cms/DesignDoc_cms.md))。

## 業務ルール

| #   | ルール                                                                   | 理由                                               | 備考                       |
| --- | ------------------------------------------------------------------------ | -------------------------------------------------- | -------------------------- |
| BR1 | 事業内容は「見積もり・販売」「加工」の二本柱で対等に見せる               | 企業情報の業務内容が2本柱で構成されているため      | 取扱製品はこの下位に紐づく |
| BR2 | 問い合わせ導線 (TEL/FAX/メール) は全ページから到達可能にする             | 主目的が訴求でも、B2B の最終目的は受発注の接点確保 | フッター + ヘッダー CTA    |
| BR3 | 会社概要の一次情報 (社名/所在地/代表/連絡先) は単一の正本 section に集約 | 表記揺れ・更新漏れを防ぐ                           | 会社情報ページを正本とする |
| BR4 | 取扱製品カテゴリは一覧として網羅性を見せる (詳細個別ページは作らない)    | カテゴリ数が多く、Phase 1 では網羅性の提示で十分   | 将来 CMS 化で詳細化を検討  |

## 入出力要件

### 入力 (企業情報.md → サイトへ配置する情報項目)

| #   | 項目                                   | 必須/任意   | 配置先 (案)             | 制約/備考                        |
| --- | -------------------------------------- | ----------- | ----------------------- | -------------------------------- |

| I2  | TEL / FAX / Eメール                    | 必須        | 会社情報 + お問い合わせ | 全ページフッターにも掲載 (BR2)   |

### 出力 (ページ / section 構成 案)

| #   | ページ       | 主な section                                                     | 優先度 | 担当する成功条件        |
| --- | ------------ | ---------------------------------------------------------------- | ------ | ----------------------- |
| P1  | トップ       | hero(理念/事業要約) / 事業概要(販売×加工) / 取扱領域サマリ / CTA | 高     | 訴求 + 信頼性 (入口)    |
| P2  | 事業内容     | 見積もり・販売 / 加工 (機械/樹脂/板金溶接/ゴム) / CTA            | 高     | 事業内容の訴求          |
| P3  | 取扱製品     | 製品カテゴリ一覧 (重複削除済・グルーピング表示)                  | 中     | 事業内容の訴求 (網羅性) |
| P4  | 会社情報     | 会社概要 / 経営理念 / 沿革 / 代表挨拶 / アクセス・地図           | 高     | 信頼性の確立            |
| P6  | お問い合わせ | 連絡先 (TEL/FAX/メール) / 問い合わせフォーム                     | 中     | 接点確保 (BR2)          |
| G   | 全ページ共通 | ヘッダー(ナビ+CTA) / フッター(会社概要要約+連絡先)               | 高     | BR2/BR3                 |

> グローバルナビ案: トップ / 事業内容 / 取扱製品 / 会社情報 / お問い合わせ。
> アクセス/地図は P4 会社情報内の section に統合する (Q2 決定)。独立ページ P5 は廃止。
> P6 のフォームは IA 上「設置する」(Q4 決定)。送信処理/バリデーション/スパム対策の機能仕様は別 spec で扱う。

## 権限要件

- コーポレートサイトは公開閲覧のみで、ロールベースのアクセス制御は対象外。
- 運用者によるコンテンツ更新は開発フロー (PR) で行うため、アプリ内権限要件は発生しない。

## 監査/非機能要件

### 監査・運用

- コンテンツ更新は PR ベース。会社概要の一次情報変更はレビュー必須 (BR3/V1)。

### 非機能(性能/可用性/セキュリティ/保守)

- 性能最優先 (Design Doc Why / What のプロダクト原則)。各ページは Astro 静的生成を基本とし、不要な React island を増やさない。
- 地図埋め込み等の外部 widget は性能予算を踏まえて導入可否を判断する (E2)。
- 情報設計は section 単位で更新しやすい粒度に保つ (将来 CMS 化を見据える)。
