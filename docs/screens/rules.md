# 画面仕様書の規約

画面仕様書のページ、API との対応、画面のモックの書き方。画面の ID の決め方は [画面仕様書の目次](index.md#画面の-id-の規則) にある。  
このディレクトリの場所は、`context/project.yml` の `screens.dir` に書く。

## 配置先と名前

画面ごとに 1 つのディレクトリを作り、テンプレートの `_template/` をコピーする。

```text
<screens.dir>/
├── _common/                    # 全ての画面のモックが読む CSS と JS。画面のディレクトリにコピーしない
│   ├── mock.css                # 外枠、構成番号の印、ツールバー
│   ├── wireframe.css           # 箱と線の見た目（wf-*）。色と角丸は --wf-* に当てる
│   ├── mock.js                 # デバイスの切り替え、構成番号の印、親のページへの高さの通知
│   ├── interact.js             # 画面の中の操作（モックの間の移動、チェック、開閉）
│   └── embed-mock.js           # 仕様書のページで読み、埋め込んだモックの高さを中身に合わせる
├── _template/                  # テンプレート。サイトに載せない
└── <画面 ID>_<画面の名前>/
    ├── index.md                # 仕様書のページ
    ├── api.md                  # 画面の項目と、画面の型、API の項目の対応
    └── mocks/
        ├── <画面 ID>.css       # この画面のモックだけの見た目
        ├── 01-initial.html     # 状態ごとに 1 枚
        └── 02-<状態>.html
```

- コピーした後に、`mocks/screen-id.css` の名前を `mocks/<画面 ID>.css` に変え、モックの `<link>` も直す。
- ディレクトリの名前は、画面 ID と日本語の画面の名前を `_` でつなぐ（例 `order-list_注文の一覧`）。URL とテストは画面 ID だけを使うので、名前を変えるときはディレクトリの名前だけを変えてよい。
- モックの名前は、2 桁の連番と状態の英語の名前を `-` でつなぐ。連番は、ページに並べる順にする。
- ページを足したら、目次の画面の一覧に足す。文書のサイトにナビゲーションの設定があれば、そこにも足す。

## 仕様書のページ

1 行目は `# <画面 ID> <画面の名前>` にし、その下に画面の用途を 1〜2 文で書く。続けて、URL、使う人、実装の表を置き、`api.md` へリンクする。

セクションは次の順に置く。

| セクション                            | 書くこと                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 構成                                  | 状態ごとに 1 つのタブ（`=== "状態の名前"`）を置き、中にモックの iframe、別タブで開くリンク、構成要素の表を置く                 |
| 要素ごとのセクション（`## <要素名>`） | 表示か活性に条件がある要素と、操作か値に説明が要る要素ごとに、概要、値のソース、表示、活性、カタログ、操作                     |
| 全体動作                              | 開いた直後の表示、複数の要素にまたがる動き、URL の search params からの復元。小見出しは [全体動作](#全体動作) の名前と順にする |
| 未決                                  | 決まっていないことと、PRD と実装の食い違い。形は [未決](#未決) にある                                                          |

- 処理と通信は書かない。書かない語と移し先は [書かないこと](#書かないこと) にある。
- タブは `=== "<状態の名前>"` の行で始め、中身を 4 つの空白で字下げする。タブの名前は状態の名前にする。
- タブの中の最初に、その状態になる条件を 1 文で書く。
- 状態はアンカーを持たないので、本文から状態を指すときはリンクにせず、「「<状態の名前>」の状態」と書く。
- iframe は `<iframe class="mock" title="…" src="mocks/…">` と書く。直後には、`<a class="mock-open" href="mocks/…" target="_blank">別タブで開く</a>` を置く。
  - 高さは書かない。仕様書のページで読む `_common/embed-mock.js` が、中身に合わせる。
  - `<details>` の中には入れない。タブの中は、タブを開いたときに `mock.js` がデバイスと番号を測り直す。
- ページの中の生の HTML は、この iframe と a だけにする。

### 書かないこと

`index.md` は、画面を使う人から見た画面を書く。処理と通信と開発の設定は書かない。

- 状態と、要素の表示と活性の条件は、画面を使う人から見た出来事で書く。
  - 例: 「注文が見つからないとき」「ログインが切れていたら」「画面を開いた後に権限を外されたとき」
- 次の語を書かない。
  - 通信の仕組み: API、リクエスト、レスポンス、HTTP のステータスの数字、リダイレクト、取り直しの回数、画面と API の間に置くサーバーの名前
  - ログインの仕組み: 認証のサーバーと IdP の名前、セッション、トークン、認証の URL の引数
  - 保存の仕組み: テーブル、レコード
  - 開発の設定: フェイクの API、モックのデータ、testid
- 例外として、次の場所には書いてよい。
  - ページの最初の表の URL と実装の行
  - カタログの欄
  - URL の search params の名前と値
  - `api.md` と Design Doc へのリンクの文字列と、リンクを案内する 1 文（「画面の項目と、API の項目の対応は API との対応にある。」）
- 書かないことの移し先は次のとおり。
  - HTTP のステータスと、状態と文言の対応は、`api.md` の [状態と失敗の要因](#状態と失敗の要因) の表に書く。
  - 処理の流れは、画面の機能の Design Doc に書く。何をどの順で読み、何を確認し、失敗をどう扱うかが入る。`index.md` からは、Design Doc のセクションへリンクする。
  - テストが指す要素と testid は、モックの `data-testid` と、`api.md` の要素の testid の表に書く。
- 入力の長さの上限のように、画面を使う人が画面で出会う制約は、その人から見た形で書く。
  - 例: 「名前は 255 文字まで入れられる。超えると保存の失敗の文が出る」

### 構成要素の表

列は `番号 | 種別 | 要素名 | 仕様` にする。

- 番号は、状態ごとに 1 から欠番なく振る。表の番号の集合と、モックの `data-m` の値の集合を同じにする。同じ番号を複数の要素に付けてよい（一覧の行など）。
- 種別は、画面の上で何を指すかが分かる語にする（ボタン、リンク、テキストボックス、チェックボックス、ラジオボタン、セレクト、ファイルの選択、表、カラム、領域、ラベル、ダイアログ、覆い、メッセージ）。表の列見出しは「カラム」、行の値は「ラベル」、見出しの下の列全体は「領域」と書き分ける。
- 要素名は、利用者が画面の上で呼ぶ名前にする。ダイアログのタイトルやページのタイトルのように文言そのものが仕様のものも、要素にする。
  - 全ての画面にある種類の要素は、[決まった要素名](#決まった要素名) にする。
- 仕様の列は、要素ごとのセクションがある要素はそのセクションへのリンクにし、セクションの無い要素は空にする。
- 要素は、それが見える状態の表にだけ載せる。ほかの状態でしか見えない要素を載せない。

### 要素ごとのセクション

```markdown
## <要素名>

**概要**: <何の要素かを、種別と合わせて示す 1 文>。<用途と役割>

**値のソース**: 利用者に見える値。文言は「」で引く。無効の見た目もここに書く

**表示**: 次の全てに当てはまるとき。

- <主語のある条件の文>
  - <分かりにくければ、理由の文>
- 次のどれかに当てはまる
  - <主語のある条件の文>
  - <主語のある条件の文>

**活性**: 次の全てに当てはまるとき。

- <主語のある条件の文>

**カタログ**: [<コンポーネント> の <ページ>](<カタログの URL>)

**操作**: <操作>と、その結果

1. 結果の詳細
```

- 要素ごとのセクションは、表示か活性に条件がある要素と、操作か値に説明が要る要素だけに置く。条件も説明も無い要素は、構成要素の表だけに載せる。
- 欄は、上の順に置く。概要のほかは、書くことが無ければ欄ごと省く。常に表示する要素、常に活性の要素、押す操作の無い要素（ラベル、領域、覆い）には、表示と活性の欄を書かない。
- カタログの欄のリンクが 3 つ以上なら、[操作とカタログ](#操作とカタログ) の箇条書きの形にする。
- 概要の 1 文目で、何の要素かを種別と合わせて示す。例: 「開いた注文の編集へ進むボタン。」
- 変数名、関数名、型、API の名前、testid は書かない。それらとの対応は `api.md` に書く。

#### 表示と活性

- 「活性」は、押すと動く（入力できる）ことを指す。送っている間に押しても動かないボタンは、その間は活性でない。無効の見た目（色を薄くする）は、活性と別に値のソースに書く。
- 表示と活性は箇条書きにし、1 行に 1 つの条件を書く。並べた条件は、全てに当てはまるときを表す。
- 「または」は、第 1 段に「次のどれかに当てはまる」と書き、その下の入れ子に条件を並べる。
- 条件は、主語のある文にする。主語は、「開いた注文」「ログインした利用者」のように、画面を使う人から見て何を指すかが分かる語にする。
- 状態が決める条件（データを読めた）は、要素の条件に書かない。要素は、見える状態の構成要素の表にだけ載るためである。要素の条件には、同じ状態の中で出たり出なかったりする条件だけを書く。
- 否定は、文の末尾を「〜でない」「〜がない」に変えて書く。例: 「開いた注文が、キャンセルした注文でない」。
- 理由が分かりにくい条件には、その条件の入れ子の箇条書きで理由を足す。
- 条件の文は、`api.md` の「条件の対応」の表に、否定でない形で同じ文を書く。点検が、2 つの文が同じかを照らす。

#### 操作とカタログ

- カタログの欄は、コンポーネントのカタログを持つときだけ書く。リンクの先は、画面の文言とデータで要素を見せるページにする。
  - 要素を描くコンポーネントのうち、カタログのページがあり、そのページに要素が出るいちばん小さいものを選ぶ。ページは、仕様書の状態に近いものを選ぶ。
  - 画面のコンポーネントのどのページにも要素が出ないときだけ、共通のコンポーネントのページを選ぶ。どのページにも出なければ欄ごと省く。
  - リンクは、`context/project.yml` の `screens.catalog_url` で始まる URL で書く。
  - 1 つの要素を 2 つ以上のコンポーネントが描くとき、仕様書の 2 つ以上の状態を別のページが描くときは、それぞれのページへのリンクを書く。
  - リンクが 2 つまでなら、「**カタログ**:」の後ろに、リンクを「、」でつないで書く。
  - リンクが 3 つ以上なら、「**カタログ**:」の後ろを空にし、空行の下にリンクを 1 つずつ箇条書きにする。「、」でつなぐと欄が 1 文になり、文の長さのチェック（120 字）を超えるためである。

    ```markdown
    **カタログ**:

    - [<コンポーネント> の <ページ>](<カタログの URL>)
    - [<コンポーネント> の <ページ>](<カタログの URL>)
    - [<コンポーネント> の <ページ>](<カタログの URL>)
    ```

- 操作の欄は、操作を起点に画面が変わるものだけを書く。無ければ欄ごと省く。
  - 操作が 1 つなら、「**操作**: 押すと注文の編集を開く。」のように操作と結果を 1 文で書き、続けて結果の詳細を番号付きの箇条書きにする。
  - 操作が 2 つ以上なら、「**操作**:」の下に、操作ごとの箇条書きを置き、入れ子に結果を書く。

### 決まった要素名

全ての画面にある種類の要素は、次の種別と要素名にする。  
同じ要素を画面ごとに違う名前で呼ぶと、画面をまたいで仕様を比べられないためである。

| 要素                                                     | 種別       | 要素名                                                                     |
| -------------------------------------------------------- | ---------- | -------------------------------------------------------------------------- |
| ページの見出し                                           | ラベル     | ページのタイトル                                                           |
| ダイアログとモーダルの見出し                             | ラベル     | ダイアログのタイトル                                                       |
| ダイアログとモーダルの後ろの覆い                         | 覆い       | 覆い                                                                       |
| フッターを出さないモーダルの右上の ×                     | ボタン     | 閉じる                                                                     |
| ダイアログのフッターの、何も変えずに閉じるボタン         | ボタン     | キャンセル（文言を「戻る」か「閉じる」にしたダイアログでも、要素名は同じ） |
| ダイアログのフッターの、確定のボタン                     | ボタン     | ボタンの文言（「保存する」「削除する」）                                   |
| データを読み終えるまでの表示                             | 領域       | 読み込み中の表示                                                           |
| 画面を開いたときにデータを読めなかったことの文           | メッセージ | 読み込みの失敗の文                                                         |
| 読み込みの失敗の文の横の、もう一度読むボタン             | ボタン     | 読み直す                                                                   |
| 読み終えた後に読み直して、読めなかったことの文           | メッセージ | 最新の情報の読み込みの失敗の文                                             |
| 最新の情報の読み込みの失敗の文の横の、もう一度読むボタン | ボタン     | 最新の情報を読み直す                                                       |
| 確定の操作が失敗したことの文                             | メッセージ | 〈操作〉の失敗の文（「保存の失敗の文」「登録の失敗の文」）                 |
| 一覧に出す行が 0 件のことの文                            | メッセージ | 〈対象〉が無いことの文（「注文が無いことの文」）                           |
| 入力の誤りを項目の下に出す文                             | メッセージ | 入力の誤りの文                                                             |
| 権限が無い人に出す見出しと説明                           | ラベル     | 権限が無いことのタイトル、権限が無いことの説明                             |

- 〈操作〉は、確定のボタンの文言を名詞にした語にする。
  - 例: 登録、保存、削除、取り込み
  - 「失敗の文」「送信の失敗の文」「取得の失敗の文」と書かない。
- 1 つの画面に 2 つ以上のダイアログがあるときは、ダイアログのタイトルを「〈ダイアログの要素名〉のタイトル」にする。例: 「削除のダイアログのタイトル」
- 確定のボタンと同じ文言のボタンがダイアログの外にもあるときは、ダイアログの中のものを「ダイアログの〈文言〉」にする。例: 「ダイアログの削除する」
- 〈対象〉が無いことの文は、データが 0 件のときと、絞り込みの結果が 0 件のときで同じ要素名にし、違いは表示の欄に書く。
- 「知らせ」「背景」「モーダルの背景」を要素名に使わない。

### 全体動作

「全体動作」の小見出しは、次の名前から選び、この順に置く。  
初期処理だけは全ての画面に置き、ほかは書くことがあるときだけ置く。

1. 使う場面: 画面を開く人と場面、頻度、その場面で要る情報
2. 決めたこと: 使う場面から決めた、カラム、絞り込み、並び順、デフォルトの表示と、その理由
3. 初期処理: 開いた直後の表示、データを読み終える前と後の表示、フォーカスの位置
4. URL の search params からの復元: 読む search params と、値ごとの表示。読まない画面は、初期処理に「URL の search params は読まない」と書く
5. 絞り込み: 絞り込みと並び順と、詳細から戻ったときの値
6. 入力の確認と送信: 入力の誤りを出す時点、確定の後の表示、失敗したときの表示
7. 変えた後の表示: 確定の後に、この画面とほかの画面の表示がどう変わるか
8. 画面の移動と履歴: ブラウザの戻ると進む、別の画面へ移った後に戻ったときの表示
9. 幅による配置: 幅で変わる配置のうち、構成の表と要素のセクションに書けないもの
10. 権限の確認: 権限で変わる表示と、画面を開いた後に権限を外された人が操作したときの表示

ほかの名前の小見出しを作らない。  
1 つの要素に閉じる動きは要素のセクションに、処理の流れは画面の機能の Design Doc に移す。

### 未決

「未決」は、「決まっていないこと」と「PRD と実装の食い違い」の 2 つの小見出しに分ける。  
項目の無い小見出しは置かない。どちらも無ければ、「未決は無い。」と書く。

```markdown
## 未決

### 決まっていないこと

- <問いの形で 1 文>
  - 今の動き: <実装か、モックの描き方>
  - 決める人: <役割>
  - 期限: <決める issue か、決めないと進めない時点>

### PRD と実装の食い違い

- <PRD が書くことと、実装がすることの違い>
  - 決める人: <役割>
  - 期限: <決める issue か、決めないと進めない時点>
```

- 決める人は、人の名前でなく、開発者、プロダクトの責任者のような役割で書く。
  - 業務の担当者に確認して決めるときは、「開発者が、業務の担当者に確認して決める」と書く。
- 期限は、決める issue の番号か、「管理の画面を作るとき」のように、決めないと進めない時点で書く。
- 今の実装で決まっていることは、未決に残さない。要素のセクションか全体動作に、今の動きを仕様として書く。
- エラーの見せ方は、規約の [エラーの見せ方](#エラーの見せ方) で決めたので、画面ごとの未決に書かない。
- ほかに画面をまたぐ未決を決める issue があれば、期限にその issue を書く。

## API との対応

`api.md` は、次の 3 つの表を持つ。失敗の状態と文を出し分ける画面は、[状態と失敗の要因](#状態と失敗の要因) の表も持つ。  
画面を作る人、API を変える人、仕様と実装を照らす人が読む。

| 見出し             | 列                                                     | 書くこと                                                                               |
| ------------------ | ------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `## 値の対応`      | `要素名 \| 表示する値 \| 画面の型の項目 \| API の項目` | 仕様書の要素名ごとの、表示する値、画面のコードが使う型の項目、API の項目（操作と項目） |
| `## 条件の対応`    | `条件 \| 判定に使う値`                                 | 仕様書の表示と活性の条件の文ごとの、実装が判定に使う値                                 |
| `## 要素の testid` | `番号 \| 要素名 \| testid`                             | `data-testid` を付けた要素ごとの testid                                                |

- 条件の対応の条件の列には、仕様書の条件の文を、否定でない形で同じ文で書く。仕様書が「〜でない」と書く条件は「〜である」に、「〜がない」と書く条件は「〜がある」にする。
  - 同じ条件を 2 つ以上の要素が使うときも、行は 1 つにする。
- 判定に使う値には、画面の型の項目か API の項目と、その値がどうなら当てはまるかを書く。例: 「`Order.cancelledAt` がある」。
- 要素の testid の番号は、構成要素の表の番号にする。同じ要素が状態ごとに違う番号を持つときは、状態ごとに行を分ける。
- 要素の testid の testid は、モックの同じ番号の要素の `data-testid` と同じ値にする。一覧の行のように `{…}` を付けた testid は、`{…}` まで同じに書く。
  - 番号の無い要素の testid は、表に載せない。モックで `data-m` を付けない入れ物、ダイアログの覆いの後ろの要素、開くと出る補足とヘルプの説明が当たる。
- `data-testid` を 1 つも持たない画面は、要素の testid の表の見出しの行だけを置き、表の後にそのことを書く。
- モックでは、構成要素の表に載せる要素に、`data-m` と `data-testid` を同じ要素に付ける。
  - 実装が testid を付ける要素と、仕様書の要素が違うときは、モックの `data-m` を、testid を付ける要素に移す。点検は、同じ要素に付いた番号と testid の組を照らすためである。

### 状態と失敗の要因

画面が失敗の状態と文を出し分けるときは、`api.md` に、状態と文言と、その要因（HTTP のステータス、エラーのコード、API に届かないこと）の対応を表にする。  
`index.md` は画面を使う人から見た出来事で書くので、どのステータスがどの状態に当たるかは、この表だけに書く。

```markdown
## 状態と失敗の要因

| 状態           | 出す文                           | 要因                                         |
| -------------- | -------------------------------- | -------------------------------------------- |
| 読み込みの失敗 | 「注文が見つかりません。」       | `getOrder` が 404                            |
| 読み込みの失敗 | 「注文を取得できませんでした。」 | `getOrder` が 404 以外の失敗、API に届かない |
```

- 状態は `index.md` の状態の名前で、出す文は `index.md` の要素の値のソースと同じ文言で書く。
- 要因には、API の操作の名前と、HTTP のステータスかエラーのコードを書く。
- 画面のコードが文を選ぶ処理のファイルは、表の後の箇条書きに書く。
- 失敗の状態と文を出し分けない画面は、このセクションを置かない。

## 画面の共通の形

行の操作、ダイアログ、データを失う操作、エラーの見せ方、補足とヘルプは、全ての画面で次の形にそろえる。  
モックでは `_common/wireframe.css` の共通のクラスで描き、画面の CSS に同じ見た目を複写しない。  
`_template/mocks/` に、入力のダイアログ（`02-form.html`）と確認のダイアログ（`03-confirm.html`）の見本がある。

### 行の操作

- 一覧の行に、行ごとのボタンを並べない。
- 行に対する操作は、行の先の詳細に置く。詳細の見出しの右に、主な操作のボタンと「…」のメニューを置く。
- 詳細の無い一覧だけ、行の右端に「…」のメニューを置く。
  - 行ですることが 1 つだけのときは、そのボタンを 1 つだけ行の右端に置いてよい。2 つ以上なら「…」のメニューにする。
- 「…」のメニューは、`wf-menu-anchor` の中に、開くボタンと `wf-menu` を置く。
  - メニューを開いた状態は、別の状態のモックにする。開いた状態のモックでは、`wf-menu` に `is-open` を付け、見えない覆いの `wf-menu-scrim` に、閉じた状態のモックへの `data-go` と `data-escape` を付ける。
  - データを失う操作の項目は `wf-menu__item--danger` にし、最後に置く。

### ダイアログ

- フッターに操作のボタンを置くダイアログとモーダルは、右上に閉じるボタン（×）を置かず、フッターのボタンで閉じる。
  - × と「キャンセル」が並ぶと、どちらを押しても同じ結果になるのかを、画面を使う人が判断できないためである。
  - 出典: [DADS のモーダルダイアログ](https://design.digital.go.jp/dads/components/modal-dialog/) の「アクションボタンがある場合は閉じるボタンを使わない」
- 入力のダイアログは、ヘッダー（`wf-dialog__header`）の左にタイトルを置く。
  - フッター（`wf-dialog__footer`）の右に、「キャンセル」と主ボタンをこの順に置く。
  - 「キャンセル」は、何も変えずに閉じる。Escape キーは「キャンセル」に当てる（`data-escape`）。
- 確認のダイアログ（`wf-dialog wf-dialog--narrow`）は、ヘッダーを置かない。
  - 本文（`wf-dialog__body`）に、問いの形のタイトルと、何が失われ何が残るかを書く。
  - フッターの右に、「キャンセル」と確定のボタンをこの順に置く。Escape キーは「キャンセル」に当てる。
  - 確定のボタンが「キャンセル」と同じく取り消しの意味に読めるとき（「予約をキャンセルする」「やめる」「変更を取り消す」）は、閉じる側のボタンの文言を「戻る」にする。「キャンセル」と並ぶと、どちらが取り消すのかを読み違えやすい。
  - 「削除する」「外す」のように、取り消しの意味に読めない確定には、「戻る」を当てない。
- どちらのダイアログも、覆い（`wf-overlay`）を押すと何も変えずに閉じる。
- 左に要約、右に入力を置くモーダル（`wf-modal`）のように中の並びが違うものも、ヘッダーとフッターは入力のダイアログと同じにする。
  - 入力の無い詳細のモーダルは、「キャンセル」の代わりに「閉じる」を置く。
  - 入力を変えていれば、「キャンセル」、Escape キー、覆いのどれで閉じるときも、破棄してよいかを確認する。
  - 幅 768px 未満では画面いっぱいに出すが、フッターを下端に固定して常に出す。
  - フッターを出さないモーダル（読み込み中と読み込みの失敗の表示）だけは、ヘッダーの右上に × を置き、Escape キーを × に当てる。
- 詳細の画面を持たない一覧で、行の先の詳細の役をするダイアログは、ヘッダーを入力のダイアログと同じにし、フッターに閉じるボタンと、その行でできる操作を並べる。
  - 閉じるボタンは、入力があれば「キャンセル」、入力が無ければ「閉じる」にする。
  - フッターの右に、閉じるボタンと、その行でできる操作をこの順に並べる。
  - 操作のどれかを勧めないときは、どれも主ボタンの色にしない。
- ダイアログとモーダルのフッターに、データを失う操作の起点のボタンを置くときは、そのボタンを 1 つだけ白い面に赤い文字（`wf-btn--destructive`）でフッターの左端に置く。閉じるボタンとほかの操作は、右にまとめる。

### データを失う操作

- データを失う操作と、取り消せない操作は、確定の前に確認のダイアログを出す。
- 確定のボタンは赤（`wf-btn--danger`）にし、ボタンの文言は「削除する」「外す」のような操作の動詞にする。
  - 「OK」と「はい」にしない。
  - 何が失われるかを示して確定する入力のダイアログでも、確定のボタンを赤にする。
- 確認のダイアログを開く起点のボタンは、白い面に赤い文字（`wf-btn--destructive`）にし、よく使う安全な操作（「閉じる」「編集」「保存」）の隣に並べない。
  - 画面の中で安全な操作と同じ行に置くときは、行の反対の端に離して置く。
  - 「…」のメニューの項目は、`wf-menu__item--danger` にする。

### エラーの見せ方

失敗は、画面を使う人が次にできることで分けて見せる。

| 失敗                       | 出す文                                                                 | 読み直す         |
| -------------------------- | ---------------------------------------------------------------------- | ---------------- |
| 対象が見つからない         | 「〈対象〉が見つかりません。」。一覧から開く画面では、開き直す先も書く | 出さない         |
| 対象を見る権限が無い       | 「この〈対象〉を見る権限がありません。」                               | 出さない         |
| 確定の操作の権限が無い     | 「この操作をする権限がありません。」                                   | 出さない         |
| 入力が保存の規則に合わない | 「入力の内容では〈対象〉を〈操作〉できません。内容を直してください。」 | 出さない         |
| ほかの失敗と、つながらない | 読み込みの失敗の文か、〈操作〉の失敗の文                               | 画面が持てば出す |

- 見つからない、権限が無い、入力が規則に合わないの 3 つは、読み直しても結果が変わらない。画面は自動で読み直さずに、すぐ文を出す。
- 入力が規則に合わないときに、合わない項目を API が返さないなら、項目の下に入力の誤りの文を出さない。
- 選択肢の一覧を読んでいる間は、フォームの代わりに読み込み中の表示を出す。
  - 読めなかったときは、フォームの代わりに失敗の文を出す。選択肢が 0 件のときと見分けられるようにするためである。
- 画面の全体を読み込みの失敗の表示に替えるのは、画面のデータをまだ一度も読めていないときだけにする。
- 読み終えた後に、ウィンドウに戻ったときなどに画面がデータを読み直して読めなかったときは、読み終えた表示を出し続ける。
  - 画面の見出しの下に、「最新の情報を読み込めませんでした。」と、読み直すのボタンを横に並べて出す（`wf-alert wf-refetch-error`）。読み上げでは警告として扱う。
  - 読み直すを押すと、読めなかったデータだけを読み直す。読めたら、文とボタンを消す。
  - 見つからない、権限が無いで読めなかったときも、同じにする。
  - 状態の名前は「最新の情報の読み込みの失敗」にする。要素名は [決まった要素名](#決まった要素名) にある。
- どの失敗がどの文に当たるかは、画面ごとの `api.md` の [状態と失敗の要因](#状態と失敗の要因) に書く。

### 補足とヘルプ

画面に常に出す説明は 1 文までにし、初めてのときだけ要る説明は、「詳しく」で開く補足か、? のヘルプに移す。

- 「詳しく」で開く補足は、常に出す 1 文の下に「詳しく」のボタンを置き、押すと続きの説明を開き、もう一度押すと閉じる。
  - `wf-more` の中に、1 文の `p`、開くボタンの `wf-btn wf-btn--text wf-more__toggle`、続きの説明の `wf-more__body` を置く。
  - 開くボタンに `data-open` と `aria-expanded="false"` を、続きの説明に同じ名前の `data-panel` を付ける。
  - 手順のように、読みながら操作する説明に使う。
- ? のヘルプは、見出しの右に ? のボタンを置き、押すと見出しの下に説明を出す。説明の外を押すか、Escape キーを押すと閉じる。
  - 見出しと ? を `wf-title` に並べ、`wf-help` の中に、開くボタンの `wf-btn wf-btn--icon wf-help__toggle` と説明の `wf-help__panel` を置く。
  - 開くボタンに `data-open` と `aria-label="ヘルプ"` を、説明に同じ名前の `data-panel` と `data-panel-dismiss` を付ける。
  - testid は、開くボタンを `<画面 ID>-help`、説明を `<画面 ID>-help-text` にする。1 つの画面に 2 つ以上置くときは、`<画面 ID>-<欄>-help` と `<画面 ID>-<欄>-help-text` にする。
  - 1〜2 文で足りる、1 つの欄か画面の全体への説明に使う。
- どちらも開閉を状態のモックにせず、各状態のモックに閉じた形で描く。開くと出る説明にも `data-m` を付けない。
  - 仕様で開いた形で始める補足は、その状態のモックで開いた形に描く。

## 画面のモック

モックは、1 つの状態を 1 枚の HTML で描く。画面の中で完結する操作（ダイアログを開く、タブを切り替える）の結果も、別の状態のモックにする。状態のモックの間は、[画面の中の操作](#画面の中の操作) の `data-go` でつなぐ。

例外として、幅で出し分ける開閉式の要素（幅 768px 未満だけで出すドロワーやメニュー）は、別の状態のモックにしない。各状態のモックに描き、閉じた状態で始め、[画面の中の操作](#画面の中の操作) の `data-panel` で開閉する。  
「詳しく」で開く補足と ? のヘルプと、`data-panel-dismiss` で開閉するメニューも、別の状態のモックにしない。形は [補足とヘルプ](#補足とヘルプ) にある。

### 構造

```html
<body data-view="desktop">
  <div class="stage">
    <div class="screen">
      <div class="screen-body"><!-- 画面 --></div>
    </div>
    <div class="markers"></div>
  </div>
  <script src="../../_common/mock.js"></script>
  <script src="../../_common/interact.js"></script>
</body>
```

- body の末尾で `../../_common/mock.js`、`../../_common/interact.js` をこの順に読む。ほかの script は書かない。
- head で `../../_common/mock.css`、トークンの CSS、`../../_common/wireframe.css`、`<画面 ID>.css` をこの順に読む。
  - トークンの CSS は、`context/project.yml` の `screens.tokens_css` に書いたファイルを、モックからの相対パスで読む。キーが無ければ読まない。
- `body` の `data-view` は最初に見せるデバイスにする。表示の幅が 600px 未満のとき（スマートフォンで仕様書を読むとき）は、`data-view` によらずモバイルで描く。`mobile`（390px）、`tablet`（768px）、`tablet-wide`（1024px）、`desktop`（1440px）から選ぶ。値は `mock.js` の `VIEWS` にだけ書く。
- サイトのヘッダーとナビゲーションは、その画面の構成要素にするときだけ描く。

### 構成番号と data-testid

- 構成要素の表の要素に `data-m="<番号>"` を付ける。座標は書かない。`mock.js` が要素の左上に番号の印を重ねる。
- 構成番号は、その状態で見える要素にだけ付ける。
- 幅で出し分ける開閉式の要素と、それを開いて初めて見える要素は、その状態で見える要素として扱い、同じ状態の表に載せて `data-m` を付ける。
  - `mock.js` は見えない要素に印を置かないので、印は開いたときに出る。
  - どの印が開くと出るかと、どの幅で出すかを、仕様書の構成のセクションかその状態の説明に、要素の名前で書く。
- テストが指す要素に `data-testid` を付ける。画面の testid は、モックの `data-testid` を元にする。
  - 形は、小文字の英語と数字を `-` でつなぎ、`<画面か部品>-<要素>` にする（例: `order-list-submit`）。
  - 一覧の行のように同じ要素が並ぶものは、末尾に `{…}` を付ける（例: `order-list-row-{注文の ID}`）。`{…}` には、どの値が入ってもよい。
  - 区分のように API の値を末尾に付けるときは、値の `_` をそのまま残す（例: `order-summary-in_progress`）。
  - テストが使う testid は、どれかのモックにある値か、モックの `{…}` の形に当たる値にする。`context/project.yml` に `screens.e2e_dir` があれば、点検がテストのコードの testid をモックと照らす。
- 例外として、全ての画面に共通する状態（[目次の全ての画面に共通する状態](index.md#全ての画面に共通する状態)）はモックを持たず、testid は目次のセクションに書く。点検は画面のディレクトリのモックだけを読むので、テストがその testid を指すときは、共通の状態を描く画面のモックを足す。
- ツールバーの「data-testid」を入れると、番号の印の横に testid を出す。

### 幅と配置

- 幅による切り替えは `@container screen (width < 768px)` のように `.screen` の幅で書く。viewport の寸法の `@media`、`vh` と `vw` は使わない。モックの中では、viewport の幅はデバイスの幅と一致しない。
- スクロールする場所は作らず、画面の高さは中身に合わせる。ただし、実装が横に送る表は、モックでも横に送ってよい。
- ダイアログ、覆い、トーストは、`.screen` の中に `position: absolute` で置く。`position: fixed` は使わない。
- 色、角丸、書体は `wireframe.css` の変数（`--wf-*`）で書く。
  - トークンの CSS を読むときは、`wireframe.css` の `:root` でセマンティックトークンを `--wf-*` に当てる。足りない色は、セマンティックトークンを `--wf-*` に当てて足す。
  - プリミティブトークンと 16 進の色は、画面の CSS に直に書かない。`wireframe.css` の `:root` で `--wf-*` に当てるときだけ使う。
- 画面だけの見た目は `mocks/<画面 ID>.css` に書く。2 つ以上の画面で使う見た目は `_common/wireframe.css` に移す。

### 禁止

- 外部の読み込み。HTML、CSS、JS に `http` で始まる URL を書かない。フォントはシステムのもの、アイコンはインラインの SVG にする。
- 実在の組織、人、連絡先。ダミーデータで描く。
- ダークモードの切り替え。

### 画面の中の操作

モックの押せる要素には、仕様書の要素ごとのセクションの操作の欄に書いた操作を付ける。  
処理は `_common/interact.js` が持ち、モックは要素の属性で操作を指す。属性は次のとおり。

| 属性                                        | 押したときの動き                                                                                                                       | 付ける要素の例                                                                                       |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `data-go="<モック>"`                        | 指したモックへ移る                                                                                                                     | 状態を変えるタブと項目、ダイアログを開くボタン、閉じるボタンと覆い、送信のボタン、別の画面へのリンク |
| `data-toggle`                               | `is-on` を付け外す                                                                                                                     | チェックボックス、トグル                                                                             |
| `data-choice="<組の名前>"`                  | 押した要素に `is-on` を付け、同じ組のほかの要素から外す                                                                                | ラジオボタン、チップ                                                                                 |
| `data-open="<名前>"`、`data-close="<名前>"` | `data-panel="<名前>"` の要素に `is-open` を付け外し、開くボタンの `aria-expanded` を変える。`data-open` は、開いている間に押すと閉じる | 幅で出し分けるドロワー、メニュー、補足とヘルプ                                                       |
| `data-escape`                               | Escape キーで押す。見えている要素だけが動く                                                                                            | ダイアログのフッターの「キャンセル」と「閉じる」、フッターの無いモーダルとドロワーの閉じるボタン     |

- `data-go` の先は、同じ画面のモックならファイルの名前（`03-detail.html`）、別の画面のモックなら `../../<画面のディレクトリ>/mocks/<モック>.html` と書く。
  - 先は、操作の欄の結果に最も近い状態のモックにする。詳細のダイアログの閉じるボタンなら、ダイアログを開く前の一覧の状態へ移る。
  - デバイス、構成番号、data-testid、幅に合わせるかの選択は、URL の search params で移った先に引き継ぐ。仕様書のページの iframe の中では、iframe の中で移る。
  - 移った先は、その状態のモックの値で描く。前のモックで変えたチェックと選択は引き継がない。
  - ファイルの選択は、ファイルの選択のダイアログを開かず、ファイルを選んだ後の状態のモックへ移す。
- 次の操作には属性を付けない。
  - API の呼び出し、保存、ダウンロード、ログアウト、ブラウザの確認のダイアログ
  - 当たる状態のモックが無い操作。期間を変える操作、文字の入力、送信中の状態から結果への移り
- 押せる要素には `interact.js` が `tabindex="0"` を付け、Enter と Space でも動かす。背景のように、キーボードで押さなくてよい要素には `tabindex="-1"` を書く。`aria-disabled="true"` の要素は押しても動かない。
- `interact.js` は、role の無い押せる要素に role を付ける。`data-toggle` には `checkbox`、`data-choice` には `radio`、ほかには `button` を付け、`checkbox` と `radio` の `aria-checked` を `is-on` に合わせる。role を書いた要素、`tabindex="-1"` の要素、`button` と `a` と `input` には付けない。
- `interact.js` は、表示を変えた後に `mockRefresh()` を呼び、番号の印を置き直す。
- `data-panel` に `data-panel-modal` も付けると、開いて見えている間は panel の外の要素の印を出さない。デバイスを切り替えると、開いている panel を閉じる。
- `data-panel` に `data-panel-dismiss` も付けると、panel と開くボタンの外を押すか、Escape キーを押すと閉じる。状態のモックにしないメニュー（ヘッダーのアカウントのメニュー）と、? のヘルプに付ける。
- panel を開くと、panel の中の最初のフォーカスできる要素へフォーカスを移す。閉じると、見えている開くボタンへフォーカスを戻す。外を押して閉じたときは、押した要素に移ったフォーカスを残す。
- 幅 768px 以上で、開閉ではなく形の切り替えになる panel には、`data-panel-wide` を付ける。幅 768px 以上では、開いても閉じてもフォーカスを開くボタンに残す。`data-panel-modal` も付けていても、幅 768px 以上では panel の外の印を隠さない。
  - 幅 768px 以上で `is-open` がたたんだ形を表す panel（開いた形で始め、押すとたたむ左の欄）は、値を `collapse` にする。`interact.js` は、幅 768px 以上では開くボタンの `aria-expanded` を `is-open` の逆にする。
  - 幅 768px 以上で `is-open` が広げた形を表す panel（たたんだ形で始め、押すと広げるナビゲーション）は、値を `expand` にする。
  - `interact.js` は、`wireframe.css` が幅 768px 以上で `[data-panel-wide]` に置く `--wf-panel-wide: 1` で幅を読む。画面の CSS で、幅 768px 以上の形を描く。
- 属性で書けない操作が要るときは、モックに script を書かず、`interact.js` に属性を足す。

モックの印の位置は、CSS の `zoom` を標準の形で扱うブラウザで確認する。

## 点検

リポジトリのルートで流すスキル write-screen-spec の `scripts/check-screens.mjs` が、規約のうち機械的に確認できるものを見る。

- 名前と仕様書: ディレクトリとファイルの名前、仕様書の 1 行目と生の HTML、状態のタブ、iframe と別タブのリンク、構成要素の表の見出し
- 番号: 表の番号とモックの `data-m` の一致、`data-m` の連番
- 操作: `data-go` の先のモックがあるか、`data-open` と `data-close` の名前の `data-panel` があるか、属性の値が空でないか、`data-escape` を操作の属性を持つ要素に付けたか
- モック: 構造と読み込みの順、`data-view`、`data-testid` の形、禁止の記述と幅と配置の規則（外部の URL、`position: fixed`、viewport の単位と寸法の `@media`、ダークモード）
- テンプレートの `<…>` の消し忘れ（`index.md`、`api.md`、モック、画面の CSS）
- カタログ: `screens.catalog_url` があるとき、カタログの欄にリンクがあり、全てがその URL の下にあるか。欄の後ろが空なら、下の箇条書きのリンクを見る
- テスト: `screens.e2e_dir` があり、全ての画面を見るとき、テストのコードがリテラルで書いた testid がどれかのモックの `data-testid` にあるか。変数で受けた testid は照らさない
- 条件: 仕様書の「**表示**」「**活性**」の下の第 1 段の文が、`api.md` の「条件の対応」の表の条件の列にあるか。第 1 段が「次のどれかに当てはまる」のときは、その下の第 2 段の文を照らす。末尾の「でない」は「である」に、「がない」は「がある」に置き換えて照らす
- testid の表: `api.md` の「要素の testid」の表の各行で、同じ番号の `data-m` と同じ `data-testid` を持つ要素が、その画面のどれかのモックにあるか。表の列が `番号 | 要素名 | testid` か

点検は、判定に使う値が実装の判定と合うかと、条件の文が仕様として正しいかを見ない。スキル write-screen-spec の「仕様と実装を読み合わせる」で、実装と照らす。

見た目（番号の位置、デバイスごとの崩れ）と操作は、モックを別タブで開き、ツールバーでデバイスを切り替え、押せる要素を押して確認する。
