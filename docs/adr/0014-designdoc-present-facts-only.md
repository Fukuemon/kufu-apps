# ADR-0014: Design Doc の各節には今の事実だけを書き、将来の計画は Open Questions / Future Work 節に集める

## Status

承認

## Context

- [Design Doc](../design/DesignDoc.md) には、Phase 1/2/3 という時系列の記述がほぼ全節に散らばっていた。
  - フェーズの展望、想定ユーザーの表の Phase 1 の優先度の列、成功条件の Phase 1 の target、スコープ、Lower-Priority Goals、設計上の前提、モジュールの責務の `apps/cms` の行に及んでいた。
- 設計の文書に今の事実と将来の構想が同居すると、読み手（開発者と AI エージェント）はどれが今の状態かを毎回見分ける必要がある。
  実装と照らし合わせる精度も下がる。
- C4 の図（System Context の L1 と Container の L2）も、要点を読み取りにくかった。
  利用者と開発のプロセス（開発者、GitHub、docs）が同じ図に並び、未実装の要素（点線の `apps/cms`）も載っていたため。
- 決定のときの L1 と L2 の構成要素は、問い合わせの backend（Cloudflare Pages Functions と Resend）を含んでいた。
  しかし、問い合わせの backend は未実装で、リポジトリに `functions/` がなかった。
  「実在の実行単位だけを載せる」という基準と食い違っていた。

## Decision

- **Design Doc の各節には、今の事実だけを書く。**
  Phase 1/2/3 のような時系列の語と将来の記述を、全節から除く。
- **将来の計画（cms の構想、UI の本格的な共有への移行など）は、`## Open Questions / Future Work` 節に集める。**
  判断の根拠は ADR へリンクし、Future Work 節のほかには将来の構想を書かない。
  - ADR-0003: [Phase 1 はコーポレートサイトだけにし、cms を後に回す](0003-phase1-corporate-site-only-and-cms-deferred.md)
- **C4 の図は L1 と L2 の階層の分け方を保ち、中身を次の基準で描き直す。** 1 枚の図には統合しない。
  - L1（System Context）は、利用者の視点に絞る。
    - 訪問者と内容の更新者、コーポレートサイト、外部のサービスだけを載せる。
    - 開発者、GitHub、docs の workflow は載せない。
    - 記法は `C4Context` をやめ、素直な flowchart にする。
  - L2（Container）は、実在する実行単位とデータの流れだけを載せる。
    - `apps/corporate-site`、`packages/ui`、`packages/config`、`e2e`、外部のサービスを載せる。
    - 未実装の `apps/cms`（点線）と、文書の群のノードは載せない。
    - cms は Future Work 節で、docs は「詳細の所在」節で扱う。
- **図に載せるのは、リポジトリに実装のコードがある実行単位と、確定した配信先だけにする。**
  仕様が決まっていても、未実装のものは Future Work 節で扱う。
  - この基準により、問い合わせの backend は L1 と L2 から外し、Future Work 節で扱う。
  - Cloudflare Pages と CDN は、確定した配信先として図に残す。
    - ADR-0001: [Terraform の infra code を別のリポジトリで管理する](0001-terraform-infra-repository-boundary.md)
  - 実装が進んだら、そのときに図へ足す。

## Considered Options

| 選択肢                                                                                                     | 強み                                                                                              | 弱み                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** 各節に今の事実だけを書き、将来の計画を Future Work 節に集める。C4 は L1 と L2 を保ち、中身を絞る | Design Doc のどの節を読んでも今の状態が分かる。将来の計画の更新が Future Work 節と ADR に限られる | 書き換えるときに、節の構成（スコープ、Lower-Priority Goals、完成条件）を組み替える手間が一時的にかかる                                                                                                                                                               |
| C4 の L1 と L2 をやめ、1 枚の図に統合する                                                                  | 図が 1 枚で済み、保守する対象が減る                                                               | 誰が何のために使うか（文脈）と、どう構成されているか（構造）が 1 枚に同居し、それぞれの読み手に余計な情報が載る。読み取りにくさの原因は図が 2 枚あることではなく、各図に開発のプロセスと未実装の要素が同居していることなので、階層を保って中身を絞る方が効果が大きい |
| Phase の記述を残し、今の Phase を明示する                                                                  | 書き換える量が小さい                                                                              | 全節に散らばった Phase の語を見分ける手間が残り、Phase が進むたびに全節を更新する必要がある。今の事実と将来を節で分ける方が、更新する箇所が Future Work 節に限られる                                                                                                 |

## Consequences

### Positive

- Design Doc のどの節を読んでも今の状態が分かり、実装と比べる精度と、AI の読解の精度が上がる。
- 将来の計画の更新が、Future Work 節と ADR に限られる。
- 図と実装が一対一に対応する。

### Negative

- 書き換えるときに、節の構成（スコープ、Lower-Priority Goals、完成条件）を組み替える必要があり、一時的に編集の手間がかかる。
- 決まっているが未実装のものは、図から読み取れない。
  Future Work 節を読む必要がある。
