# ADR-0006: corporate-site の IA を 5 ページ構成から 3 route の統合構成へ変更する

## Status

承認

## Context

- corporate-site の IA は、5 ページ構成として確定していた。
  - 構成は、トップ `/` / 事業内容 `/services` / 取扱製品 `/products` / 会社情報 `/company` / お問い合わせ `/contact` と、共通のレイアウト G である。
  - feature doc を IA の基準としていた。
- デザイン制作のワークフローを定めるパイロットの対象を選ぶ中で、「そもそも多ページにする必要があるか」という IA のレベルの問いが出た。
  - ADR-0004: [デザイン制作のワークフロー](0004-design-production-workflow.md)
- この問いは、机上の比較ではなく、ADR-0004 で確定した design-workflow（A0 → A 発散 → import → B 収束）を実走して評価し直した。
  - 実プロト（`design/features/corporate-site/index.pen`）でデザイン方針を 16 版にわたって反復し、IA を評価した。
- 実走の結果、事業内容と会社情報は LP 内の section で十分な密度を持てることが実プロト上で確認できた。
  - 一方、取扱製品（18 カテゴリ × 延べ約 320 社のメーカーの一覧）は、分量から独立したページが必要である。

## Decision

- corporate-site の IA を **3 route の統合構成** にする。
  - `/` — LP。hero / 事業紹介（旧 P2 事業内容を section に統合）/ 取扱製品の索引（18 カテゴリ）/ 会社情報（旧 P4 会社情報を section に統合）/ フルフッター
  - `/products` — 取扱製品。18 カテゴリの詳細（INDEX パネル + 全メーカーの一覧）
  - `/contact` — お問い合わせ。連絡先 + 問い合わせフォーム
- `/services` と `/company` の単独の route は設けない。
  - 事業内容・会社情報への直接の導線は、LP 内のアンカーで提供する。
- IA の基準は、引き続き feature doc の「ページ構成」とする。
  - 出典: [ページの構成](../../apps/corporate-site/DesignDoc.md#ページの構成)
- デザインの基準は、実装（コード + Storybook）とする。
  - ADR-0012: [デザインの基準を実装とし、Pencil（`.pen`）を廃止する](0012-design-source-of-truth-implementation.md)

## Considered Options

| 選択肢                                                       | 強み                                                                                                                                                                                                                                                                                                           | 弱み                                                                                                                                                                                                                 |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** 3 route の統合構成（`/`、`/products`、`/contact`） | コンテンツの密度と分量に応じた構成にできる。薄い情報は LP に統合し、分量のある取扱製品と、機能を持つお問い合わせだけを独立させる。LP の 1 ページで訴求 → 信頼 → 接点の流れが完結しつつ、`/products` と `/contact` を直接共有できる。design-workflow の実プロトの反復（デザイン方針の 16 版）で妥当性を検証した | 事業内容・会社情報の個別の URL がなくなり、ページ単位の SEO は 5 ページ構成より弱い。LP が縦長になるため、画像の lazy-load などの初期ロードの最適化が実装のときに必要になる                                          |
| 多ページ（5 ページ）構成を維持する                           | 確定済みの IA をそのまま引き継げる。ページ単位の SEO（個別の title / description）を最大化できる                                                                                                                                                                                                               | 事業内容・会社情報は実コンテンツの量が少なく、独立ページにすると密度が薄くなる（実プロトで確認）。ページ数に比例して、制作・保守・E2E のコストが増える。訪問者の回遊が分断され、訴求 → 信頼 → 接点の流れが切れやすい |
| 完全な単一の LP（1 route）にする                             | 制作・保守のコストが最小。回遊が 1 ページで完結する                                                                                                                                                                                                                                                            | 取扱製品（18 カテゴリ × 全メーカーの一覧）を載せると LP が過長になり、初期ロードと走査性を損なう（実プロトで確認）。問い合わせフォームを独立した URL で共有・誘導できない                                            |

## Consequences

### Positive

- 実装の対象が 3 route に絞られ、制作・保守・E2E のコストが下がる。
- 3 route の IA と実装（+ Storybook）が 1:1 で対応する。
- design-workflow の A→B のパイロットの検証を兼ねた、実プロトに根拠のある IA の決定として残る。

### Negative

- `/services` と `/company` を前提にした文書・ナビの設計は、更新が必要になる。
- 将来コンテンツが増えて、事業内容・会社情報を独立したページへ戻す場合は、IA を再び変更することになる（その際は本 ADR を置換する）。
