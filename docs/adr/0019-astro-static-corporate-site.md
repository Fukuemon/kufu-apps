# ADR-0019: コーポレートサイトを Astro の静的な生成で作り、UI を共有の package に置き、CMS を最初から作らない

## Status

承認

## Context

- 主な目的は、Astro によるコーポレートサイトを、高い表示の速さと保守のしやすさを保って公開することである。
- コーポレートサイトは、表示の速さ、情報の分かりやすさ、公開の前の検証が重要である。
- コーポレートサイト、共通の UI、設定が別々に成長すると、構成と品質の基準が分散しやすい。
- monorepo の価値は、再利用のしやすさと一貫性にある。

## Decision

- コーポレートサイトを Astro の静的な生成で作り、React の SPA にしない。
  - 主な価値はコーポレートサイトの速い公開と保守のしやすさで、Astro のほうが適しているため。
- UI を app ごとに作らず、共有の package に置く。
  - monorepo の価値は再利用のしやすさと一貫性にあるため。
- CMS と API を最初から作らない。
  - 主な目的は Astro のコーポレートサイトの構築で、CMS は必要性が具体的になってから判断するため。
  - ADR-0003: [Phase 1 は corporate-site だけを実装する](0003-phase1-corporate-site-only-and-cms-deferred.md)

## Considered Options

| 選択肢                                                                         | 強み                                                                     | 弱み                                                                   |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| **採用:** Astro の静的な生成で作り、UI を共有の package に置き、CMS を後に回す | コーポレートサイトの性能と静的な生成の利点を保てる。デザインと挙動が揃う | CMS の要求が出たときに、改めて判断する必要がある                       |
| コーポレートサイトも React の SPA で作る                                       | React の app と技術を揃えやすい                                          | 不要な JavaScript が増えやすく、性能と静的な生成の利点を失う           |
| app ごとに UI を個別に実装する                                                 | 最初の実装は速い                                                         | デザインと挙動が分かれ、保守のコストが上がる                           |
| 最初から CMS と API を作る                                                     | 内容の更新の自由度が高い                                                 | コーポレートサイトの公開に対して複雑さが大きく、運用と認証の設計も要る |

## Consequences

### Positive

- コーポレートサイトの表示の速さを損なう React 化を避けられる。
- UI と設定の置き場を迷わずに決められる。

### Negative

- 内容の更新は、CMS を入れるまでリポジトリの文書と pull request で行う必要がある。
