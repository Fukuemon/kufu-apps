# ADR-0011: spec を残し、issue を閉じるときの削除をチェックと削除の pull request の自動の起票で徹底する

## Status

承認

## Context

- spec は issue ごとの作業の文書で、issue を閉じるときに削除する（closeout）。
  - 削除の前提は、残す設計の成果を design、context、ADR へ移し終えていることである。
- 実際には closeout が行われず、閉じた issue の spec のディレクトリが 9 つ `specs/` に残り、取り決めと実態が食い違っていた。
- 検討の初めには、spec という中間の文書そのものを廃止し、issue の本文と design、ADR にまとめる案も検討した。
- 残っている spec を検出する `pnpm check:specs` は、検出するだけで、削除は手作業だった。
- 削除の前提である「残す設計の成果を移し終えたか」は、機械では判定できない。
  - 残っていた spec を片付けたときには、移していない設計の情報が 6 件見つかった。そのうち 1 件は、ADR と実装が矛盾していた。
  - 自動で消していれば、これらは失われていた。

## Decision

- **spec の運用（作る、設計する、移す、閉じるときに削除する）は今の取り決めのまま残す。** 廃止しない。
- 閉じるときの削除は、**チェックのスクリプト**で担保する。
  - スクリプトは、spec のディレクトリの issue の番号とトラッカーの issue の状態を照らし合わせ、CLOSED の issue の spec が残っていれば失敗する。
  - 実行は手動（コマンドの登録）にし、CI での常設化は CI のパイプラインの方針で判断する。
  - lefthook（pre-commit、pre-push）には入れない。`gh` を呼ぶので、オフラインのときと速度に影響するのを避ける。
- チェックの仕組みは**このリポジトリの中に閉じる**（スクリプト、コマンドの登録、[conventions.md](../context/conventions.md#チェックの実行点) への記載）。
  - 他のリポジトリにも広がる共有の closeout の手順へチェックの実行を足す改修は、このリポジトリでは行わない。
- issue の close を契機に、GitHub Actions が **spec を削除する pull request を起票する**。
  - bot は候補を示すだけにし、**削除してよいかは、その pull request を merge するかどうかで人が決める。**
  - pull request の本文に、設計の成果を移し終えたかを確かめるチェックリストを載せ、人のレビューとして判断を残す。
  - 対象の spec がなければ何もしない。同じブランチの pull request が既に open なら、起票し直さない。
  - `workflow_dispatch` で issue の番号を指定して、手でも実行できる。workflow が障害を起こしたときの逃げ道にする。
  - pull request を close すれば spec は残り、`pnpm check:specs` は残っているものとして検出し続ける。
- issue を閉じる pull request（`Closes #N`）に spec の削除を含めると、close の時点で spec がないので起票されない。
  - どちらでもよいが、**同じ pull request に含める方が、develop に spec が残る期間が生じない。**

## Considered Options

| 選択肢                                                                                                    | 強み                                                                                                                                        | 弱み                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** spec を残し、閉じるときの削除をチェックのスクリプトと削除の pull request の自動の起票で徹底する | 今の事実を読む場所が design、context、ADR に 1 つに決まる。closeout の削除忘れを検出できる。削除の判断を人に残す                            | チェックを手で実行する間は、実行を忘れるおそれが残る                                                                                                                                                                                                                                      |
| spec を廃止し、issue の本文と design、ADR にまとめる                                                      | 中間の文書がなくなり、基準となる文書の種類が減る。issue の本文が作業の記録を持ち、design を直接編集して pull request の差分でレビューできる | 論点、受け入れ基準、実装の分割の置き場が issue のコメントに散らばる。新しい文脈で spec を評価するレビューの対象を差し替える再設計が要り、共有のプロセスとの差が大きい。問題は spec があることではなく closeout が徹底されないことで、取り決めどおり削除が回れば運用の負荷の課題は解消する |
| チェックを lefthook か CI にすぐ組み込む                                                                  | 強制する力が最も強い                                                                                                                        | lefthook は `gh` を呼ぶので、オフラインのときと commit の速度に影響する。CI は方針そのものが決まっていなかった。手で実行できるスクリプトを先に用意し、常設化は CI の方針で判断する方が段階的で安全である                                                                                  |
| 閉じた issue の spec を自動で削除する                                                                     | 削除の手作業がなくなる                                                                                                                      | 移し終えたかは機械で判定できず、移していない設計の情報が失われる                                                                                                                                                                                                                          |

## Consequences

### Positive

- 今の事実を読む場所が design、context、ADR の 1 つに決まり、食い違った spec が残らない。
- 取り決めと実態の食い違いをチェックで検出でき、closeout の削除忘れが仕組みの上で起きにくくなる。
- 削除の手作業がなくなり、判断だけが残る。

### Negative

- チェックのスクリプトを手で実行する間は、実行を忘れるおそれが残る。CI で常設化するまでの暫定である。
- 削除の pull request を起票するには、GitHub Actions に pull request を作る権限を与えるリポジトリの設定が要る。
